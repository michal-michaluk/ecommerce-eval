## Gaps

- **P6 — unproven, both halves.** No `DraftPrivacyTest` exists, so the row cannot fail; and "payloads match the 13 schemas" is
  evidenced only by two suites being green, not by an observed comparison. The "no draft ever leaves" invariant is covered in
  pieces, none a named gate: `ShoppingEventsOfOfferTest.publishesNothingWhenTheDraftIsEdited()`
  (`src/test/java/shop/catalog/offer/ShoppingEventsOfOfferTest.java:97`) proves the event side;
  `ScopeGuardTest.enforcesTheDraftComponentsScopePerWriter` / `refusesAComponentNobodyOwns`
  (`src/test/java/shop/catalog/ScopeGuardTest.java:140,203`) and `OfferDraftControllerTest.refusesTheWholeDraftToSales()`
  (`src/test/java/shop/catalog/offer/OfferDraftControllerTest.java:154`) prove the `GET`/write scope side. **"No log carries an
  unpublished draft" is asserted nowhere.** To close: give P6 a command matching the tests that exist, or write `DraftPrivacyTest`
  including the log clause.
- **P8 — unproven, no partial score either.** PITest stops in the line-coverage phase because its own run of the suite is not
  green: `build.gradle:66-71` excludes `**/e2e/**` from the `test` task and the `pitest` block at `build.gradle:103-110` carries
  no such exclusion, so PITest boots the application and runs the whole `e2e/catalog-http-api.hurl` contract against the same
  containers between test classes. Context scoping cannot rescue the row — PITest still sends every test class to its minion. To
  close: make the suite PITest-green (isolate the shared Postgres/Kafka state, or exclude the e2e suite from `pitest`), then
  re-run; until then no mutation score exists for any context.
- **P1 — the suite is flaky, and it is the same defect P8 hits.** The first `clean build` in this session failed on
  `ReadsRebuildTest.rebuildsThePendingListFromTheReviewsOwnState()` (`ReadsRebuildTest.java:76`, `AssertionFailedError`); the
  retry passed 660/660. Under PITest the same class of failure appears as `OfferControllerTest.listsOnePageAndThePageAfterIt()`
  and `CatalogHttpApiE2eTest.runsEveryRequestOfTheContractOfElement12()`, both green under `./gradlew test`. Row PASS is the
  retry's result and is recorded as such — a green P1 is not reproducible on demand.
- **P1 — process note.** `./gradlew build` alone returns `12 up-to-date` and would "pass" while proving nothing; the recorded
  figures come from `./gradlew clean build`.
- **P2 — the property is only proved because the packages are not empty.** `allowEmptyShould(true)` is on all six rules of all
  five suites, as `spec.md:163` demands, which also means the row would go green on five empty context packages. The evidence it
  is not vacuous is indirect: the same suites pass while `src/main/java/shop/catalog/{offer,pricing,quality,reads,review}` carry
  the classes P1's coverage and `sqt` measured.
- **P3 — partial, despite the PASS.** The spec's criterion is exit 0 only, but the row's property ("the code obeys the shape
  rules") is wider than what exit 0 proves: `9 skipped`, `40 ignored`, `5 681 not evaluated`, 4 `.storybook/*.js` files with
  "incomplete element coverage", and the 59 violations are hints/warnings `sqt` is configured never to fail on. Nothing
  error-severity was reported.
- **P4 — spec drift.** `spec.md:165` expects "18 + 11 + 10 + 8 scenarios green" and that holds, but the suites hold 25 / 14 / 15 / 10
  tests; the extra 7 / 3 / 5 / 2 are unit tests of the same policies, not scenario rows. The row is PASS either way; the spec
  number understates the suites.
- **P5 — narrowed by 12 itself.** "Every error path" means every path a client can reach: `12-catalog-http-api.md:11-12` states the
  optimistic-lock row and the unexpected `500` row cannot be reached, so 106 requests prove the reachable set and nothing more.
- **P7 — undisclosed deviation, now disclosed.** The spec's command is
  `node verify-storybook.frames.cjs http://127.0.0.1:6010 --flow flows.json`; this session ran `node verify-storybook.frames.cjs`
  with no arguments. Behaviour-equivalent — `.storybook/verify-storybook.frames.cjs:29-33` defaults the url to
  `http://localhost:6010` and `--flow` to `flows.json` beside the script — but two things differ from what the spec's command
  implies: `localhost` instead of `127.0.0.1`, and the gate **self-served** its static build because nothing answered on 6010, so
  the "point the gate at an already-running gallery" path was never exercised. Spec drift: `spec.md:168` asks for "3 flow
  chains", `flows.json` carries 7, and all 7 pass.
- **The node's own gate is a false pass in this shell.** `grep -c '^| P' docs/prove-of-done.md` resolves to
  `~/.local/fs-compat/agent-bin/grep`, which drops the bare `|` from the pattern and returns the file's line count instead:
  it answers `44` on a 44-line file and `8` on an eight-line file with no match at all. `/usr/bin/grep -c '^| P'` and
  `grep -c '^[|] P'` both return the true `8`. Hardening for the spec/plan, not this doc: use `/usr/bin/grep -c '^[|] P'` and
  require one PASS/FAIL per row in the verdict column.
